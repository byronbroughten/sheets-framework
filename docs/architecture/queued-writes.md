# Queued writes and the flush

Map fragment. Sibling headings live in this folder. What a run sees between fetch and flush: [the working view](./working-view.md).

A write mutates local state and queues a request; one `batchUpdate` per flush sends them in a fixed order by kind. A flushed row delete or mid-Table column insert makes indexes stale, and a new write method asserts they aren't. The rules for adding a write: [`src/02_SpreadsheetRaw/AGENTS.md`](../../src/02_SpreadsheetRaw/AGENTS.md).

## Writes queue locally until a flush

`update`/`append`/`delete` don't hit the API — they mutate the working view and register the change on that sheet's `writeQueue`. Nothing reaches the spreadsheet until `batchUpdateGSheets()` turns each sheet's queued changes into update requests and `RawSource.flush` sends them. `GoogleSheetsAPI` maps each local operation onto Google request kinds (`updateCells`, `pasteData`, `repeatCell`, `appendCells`, `updateTable`, …) and one `batchUpdate`.

## A new write is queued and gathered on the sheet

A new write is queued and gathered on the sheet, and the flusher only sends the batch (the rules for a new write: [`src/02_SpreadsheetRaw/AGENTS.md`](../../src/02_SpreadsheetRaw/AGENTS.md)). The sheet, row or cell builds the request, either when the write is queued (`SheetRaw.updateTitle`) or from the write queue at flush time (`SheetRaw.gatherFillRequest`). Row deletes, still built in `SpreadsheetFlusherRaw`, are the one exception. A new request kind therefore settles four things: its queue op, the state that holds it, the gather method that builds it (none for a spreadsheet-level op like `addSheet`, since a tab that doesn't exist yet has no sheet state to gather from), and its slot in the send order below.

## Flush order

Within a flush the requests go out in a fixed order: add-sheet, then add-Table, then sheet title updates, table name updates, table column-property updates, appends, column inserts, fills, per-cell updates, checkbox validations, find-and-replaces, row deletes highest-index-first, then sorts, then conditional-format deletes highest-index-first, then conditional-format adds, then edit-protection deletes, then edit-protection adds, then raw. Add-sheet and add-Table lead the batch because a Table can only be added to a tab the same batch has created, and both are queued on the spreadsheet (`SpreadsheetRaw.gatherAddSheetRequest` / `gatherAddTableRequest`) rather than on a sheet, since a tab that does not exist yet has no sheet state to hold them and nothing is gathered per sheet. Google refuses an add-sheet at a GID another tab already holds, so the request always carries `sheetId` and the refusal comes back from the API. An add-Table operation goes out as two requests: an `addTable` whose `tableId` is the Table's name, then an `updateTable` carrying its column names and types, because Google writes `addTable`'s own column names three columns right of the Table, and fails with a 500 when those columns don't exist (measured on the dev spreadsheet, 23 September 2026). A seeded value on an added tab is queued on the spreadsheet too, by `SpreadsheetRaw.gatherAddedSheetCellRequest`: it is built when queued and sent in the per-cell updates slot, so it lands on the tab the same batch created. It is refused unless that GID's add-sheet is queued in the same flush, which keeps a write to an existing tab going through `CellRaw`. A checkbox (a `BOOLEAN` data-validation rule) is queued by `CellRaw.addCheckboxValidation`, or on an added tab by `SpreadsheetRaw.gatherAddedSheetCheckboxValidationRequest` under the same add-sheet guard, and sent right after the per-cell updates, so a seeded unticked `false` is written before its rule. A column-property update is one `updateTable` per Table, sending every fetched column's `columnName` and type, because a partial `columnProperties` list replaces the rest. It goes first so a header write in the same flush renames the column rather than being reverted by the stale name. Appends therefore land **before** the deletes queued beside them, and same-sheet deletes go descending because each one shifts the rows beneath it. Conditional-format deletes use the same descending-index reason as row deletes: each removal renumbers the rules beneath it. Adds follow those deletes so a remove-then-re-add in one flush lands in the order it was queued. Edit-protection deletes are by id, so they do not need descending order.

## Stale row indexes after a flush

After row deletes are sent, that sheet's **row indexes** are **stale**. Both axes use that word: the row flag is a boolean (`rowIndexesAreStale`); column stale stays a watermark (`firstStaleColIndex`). A flush that added or deleted a conditional format rule sets a third per-sheet flag (`conditionalFormats.isStale`); a second rule-mutating flush against that sheet is refused until a refetch of its rules clears it. A flush that added or deleted an edit protection sets a fourth (`editProtections.isStale`); reading or mutating that sheet's protections is refused until a refetch. Every queue-time write whose flushed request will embed a row coordinate — `updateCells` range, `repeatCell` range, `pasteData` `coordinate.rowIndex`, row `deleteDimension`, both conditional-format rule operations, and a protection whose range or unprotected ranges carry row coordinates read off the sheet — throws because the method's **first line** called `this.sheet.activeTable.assertRowIndexesNotStale()` (or the equivalent on `ActiveTableRaw`). A whole-column protection is exempt from that row check and instead calls `validateColIndexNotStale` on its column index. A whole-sheet protection with no unprotected ranges is exempt from both. A new write method ships that assert in the same change; a method that only happens to read `endRowIndex` is not gated. `endRowIndex` still throws; the rest of the table object (column range, declared types, validation values, validation condition types) stays readable. Integrating sheet properties afterwards replaces the stored Table range and column properties from the payload but does **not** clear row-index stale — `clearRowIndexStale` is the only restore, unused in production, and nothing in fetch or integrate calls it. Reads by row index stay allowed and may lie. Hybrid cache after a partial refetch, a cross-sheet copy, and content-addressed find/replace are how a lying read can still damage integrity; a later restore without clearing local row state is unsafe.

## Stale column indexes after a column insert

A column insert **not** at the Table end marks column indexes at and to the right of the insert stale; writes at those indexes throw, naming the first stale column index, while reads do not consult that watermark. An insert at the live Table end only grows the exclusive end column. A sheet may carry several column inserts, each one sent in queue order; a mid-Table insert refuses to sit beside another insert on that sheet, and a second insert must land at the Table end plus the inserts already queued, because each insert shifts the indexes the next was computed against. The two stale axes are separate: a column insert does not stale row indexes, and a flushed row delete does not stale column indexes. Rule-index stale is the third and protection-list stale the fourth, and both are independent of the row and column axes.

## Appends collapse to one request per sheet

A table's `appendCells` requests collapse into **one request per sheet**, with a `rows` entry per appended row: Sheets' table-aware append targets the same first free row for every request in the batch, so N separate one-row appends only grow the table by one while the per-cell updates still land on the rows beneath it.

## `updateColumnType` has three limits

**`updateColumnType` has three limits.** One update per fetch: the flush clears the Table's fetched column list, so another update before a refetch throws. It refuses, before anything is sent, when the same flush inserts a column on that sheet, and on a Table with a validated column, because a restore resets its dropdown style and colours.

## Per-cell writes merge value, formula and colour

Most writes queue per cell and flush as one `updateCells` request each; a cell's queued entry holds an optional value, an optional formula, and an optional background colour (`RgbColor` in the Source tier, mapped to Google `Color` only inside `GoogleSheetsAPI`), merged across writes, so a value and a colour on one cell still cost one request and neither can cancel the other. A value and a formula are mutually exclusive on that same entry: writing one drops the other. Each request's field mask is built from what that entry actually holds, so a colour-only write can't blank the cell's value and a value-only write can't blank its colour — which is how a per-cell message written over a column-wide fill keeps the fill's colour unless it names its own.

## Column fills

A column write instead queues one sheet-level *fill* per contiguous run of rows: `updateAllCells` fills every table data row of a column in one `repeatCell`, and `updateActiveCells` fills only the column's active rows, so stamping a selection costs no more requests than the selection is wide.

## Formula writes

`updateAllFormulas` / `updateActiveFormulas` are the formula-column siblings of those fills, and `updateFormula` is the per-cell sibling of `updateValue`. Both are exposed from `ColumnRaw`/`CellRaw` up through Identified and Named under the same names. Named type-restricts the three formula methods to formula columns; Identified runtime-refuses a formula write on a non-formula column; `GoogleSheetsAPI` serializes a string that already starts with `=` as `pasteData` with `PASTE_FORMULA` (RFC4180-quoted fields, tab delimiter, identical text on every row of a fill) and does not consult `isFormula`. Colour on the same change still serializes as today's `repeatCell` / `updateCells` colour path, so a formula-plus-colour flush is two requests in one `batchUpdate`. A formula string that does not start with `=` throws before anything is queued — the `=` is not prepended. A formula write does not mirror into local cell state, so a later read in the same run still sees the old effective value (colour-only writes are the precedent).

## Fills land before per-cell updates

Two consequences are invisible at the call site: fills are ordered **before** per-cell updates within a flush, so a per-cell write on a filled column wins regardless of which was queued first; and a fill's last row is snapshotted when queued, so it never reaches a row appended after it. State is still mirrored row by row for *value* fills — only the request collapses. `updateAllCells` and `updateAllFormulas` throw on a sheet that `SheetRaw.removeRowsExcept` has pruned to a selection, since a whole-column fill ignores active rows and would reach exactly the rows the prune excluded.

## `findReplace` invalidates every read

**`findReplace` is the one write that names no coordinates, and it pays for that by invalidating every read.** It carries Google's own fields — `find`, `replacement`, `matchCase`, `matchEntireCell`, `searchByRegex`, `includeFormulas` — and a scope of a range, a sheet, or the whole spreadsheet, so `ColumnNamed`/`SheetNamed` build the scope while both strings stay plain: the value config governs neither, because Google matches the cell's text. It rides the same queue and the same dry run, and sits **after** per-cell updates because it reads the text as it stands mid-batch, so text queued beside it must land first. Two consequences follow from matching by content. Nothing can be mirrored into local state, since what matched is unknowable locally, so the flush marks **every** sheet's fetched cells stale — one rule rather than a scope-dependent one — and a read afterwards throws naming the findReplace until the next fetch clears it. A coordinate formula write (`updateFormula` / `updateAllFormulas` / `updateActiveFormulas`) is the other formula touch: it stamps a new formula onto a formula column by cell or fill as `pasteData` / `PASTE_FORMULA`, so Sheets runs the UI parser (table references included) rather than storing an unparsed `formulaValue`, and it does not invalidate reads. Colour may ride beside that paste in the same `batchUpdate`. `includeFormulas` remains the text-level rewrite of a formula already in place. `validateDataNotFormula` still refuses to *write a value* onto a formula column, because a formula written as a value misbehaves in Apps Script.

## One queue shared by reference, and discarding it

That `spreadsheetStateRaw` is threaded **by reference** through `spreadsheetNamedProps` into every collaborator getter, so an endpoint, its `ConfigCoordinator`, and every operator beneath it all share one queue. A flush therefore commits everything queued anywhere in the run, not just what the calling object queued — which is why a failure path must `discardQueuedChanges()` before writing status, or the `finally` flush ships a half-finished sync. Discarding resets both write queues as groups (the spreadsheet's `updateRequests` and every sheet's `writeQueue`) rather than re-initializing individual fields. It leaves the working view reflecting writes that never happened, so it's a terminal step only.
