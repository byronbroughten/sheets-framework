# Queued writes and the flush

Map fragment. Sibling headings live in this folder. What a run sees between fetch and flush: [the working view](./working-view.md).

A write mutates local state and queues an operation; one `batchUpdate` per flush sends them in a fixed order by kind. A flushed row delete or growth makes row indexes stale, and a new write method asserts they aren't. The rules for adding a write: [`src/02_SpreadsheetRaw/AGENTS.md`](../../src/02_SpreadsheetRaw/AGENTS.md).

## Writes queue locally until a flush

`update`/`append`/`delete` don't hit the API — they mutate the working view and register the write on that sheet's `writeQueue`. Nothing reaches the spreadsheet until `batchUpdateGSheets()` turns each sheet's queued writes into write operations and `RawSource.flush` sends them. `GoogleSheetsAPI` maps each local operation onto Google request kinds (`updateCells`, `pasteData`, `repeatCell`, `insertRange`, `updateTable`, …) and one `batchUpdate`.

## A new write is queued and gathered on the sheet

A new write is queued and gathered on the Table, and the flusher only sends the batch (the rules for a new write: [`src/02_SpreadsheetRaw/AGENTS.md`](../../src/02_SpreadsheetRaw/AGENTS.md)). The sheet, row or cell builds the operation, either when the write is queued (`TableRaw.updateTitle`) or from the write queue at flush time (`TableRaw.gatherFillColumnOperation`). A new operation kind therefore settles four things: its queue key, the state that holds it, the gather method that builds it (none for a spreadsheet-level op like `addSheet`, since a tab that doesn't exist yet has no sheet state to gather from), and its slot in the send order below.

## Flush order

Within a flush the requests go out in a fixed order: add-sheet, then add-Table, then sheet renames, Table renames, Table column-property sets, Table growth, column inserts, column fills, cell writes, checkbox validations, find-and-replaces, row deletes highest-index-first, then sorts, then conditional-format deletes highest-index-first, then conditional-format adds, then edit-protection deletes, then edit-protection adds, then raw. Add-sheet and add-Table lead the batch because a Table can only be added to a tab the same batch has created, and both are queued on the spreadsheet (`SpreadsheetRaw.gatherAddSheetOperation` / `gatherAddTableOperation`) rather than on a sheet, since a tab that does not exist yet has no sheet state to hold them and nothing is gathered per sheet. Google refuses an add-sheet at a GID another tab already holds, so the request always carries `sheetId` and the refusal comes back from the API. An add-Table operation goes out as two requests: an `addTable` whose `tableId` is the Table's name, then an `updateTable` carrying its column names and types, because Google writes `addTable`'s own column names three columns right of the Table, and fails with a 500 when those columns don't exist (measured on the dev spreadsheet, 23 September 2026). A seeded value on an added tab is queued on the spreadsheet too, by `SpreadsheetRaw.gatherAddedSheetFillCellOperation`: it is built when queued and sent in the cell writes slot, so it lands on the tab the same batch created. It is refused unless that GID's add-sheet is queued in the same flush, which keeps a write to an existing tab going through `CellRaw`. A checkbox (a `BOOLEAN` data-validation rule) is queued by `CellRaw.addCheckboxValidation`, or on an added tab by `SpreadsheetRaw.gatherAddedSheetCheckboxValidationOperation` under the same add-sheet guard, and sent right after the cell writes, so a seeded unticked `false` is written before its rule. A column-property set is one `updateTable` per Table, sending every fetched column's `columnName` and type, because a partial `columnProperties` list replaces the rest. It goes first so a header write in the same flush renames the column rather than being reverted by the stale name. Growth therefore lands **before** the deletes queued beside it, and same-sheet deletes go descending because each one shifts the rows beneath it. Conditional-format deletes use the same descending-index reason as row deletes: each removal renumbers the rules beneath it. Adds follow those deletes so a remove-then-re-add in one flush lands in the order it was queued. Edit-protection deletes are by id, so they do not need descending order.

## Stale row indexes after a flush

After row deletes are sent, the **row indexes** of every Table on that sheet are **stale** (`rowIndexesAreStale`). After growth is sent, the same flag is set on the grown Table and on every Table the growth pushed down ([stacked Tables](#stacked-tables-grow-in-one-batch)); a side-by-side neighbour, a Table below whose columns don't overlap and a Table above stay unflagged. Nothing clears it within the run, because a run flushes its growth once, and the throw names the Table and says it needs a refetch in a new run. A flush that added or deleted a conditional format rule sets a second per-sheet flag (`conditionalFormats.isStale`); a second rule-mutating flush against that sheet is refused until a refetch of its rules clears it. A flush that added or deleted an edit protection sets a third (`editProtections.isStale`); reading or mutating that sheet's protections is refused until a refetch. Every queue-time write whose flushed request will embed a row coordinate — `updateCells` range, `repeatCell` range, `pasteData` `coordinate.rowIndex`, a row delete's `deleteRange`, both conditional-format rule operations, and a protection whose range or unprotected ranges carry row coordinates read off the sheet — throws because the method's **first line** called `this.table.assertRowIndexesNotStale()` (or the same call on the Table itself). A whole-column protection, and a whole-sheet protection with no unprotected ranges, are exempt from it. A new write method ships that assert in the same change; a method that only happens to read `endRowIndex` is not gated. `endRowIndex` still throws; the rest of the table object (column range, declared types, validation values, validation condition types) stays readable. Integrating sheet properties afterwards replaces the stored Table range and column properties from the payload but does **not** clear row-index stale — `clearRowIndexStale` is the only restore, unused in production, and nothing in fetch or integrate calls it. Reads by row index stay allowed and may lie. Hybrid cache after a partial refetch, a cross-sheet copy, and content-addressed find/replace are how a lying read can still damage integrity; a later restore without clearing local row state is unsafe.

## Row deletes shift only the Table's columns

No queued operation deletes whole sheet rows. `RowRaw.delete` sets a delete flag in its Table's write queue, keyed by row index, so a delete on one Table never flags a neighbour's row. The flush gathers each flagged row with `RowCommonRaw.gatherDeleteTableRowsOperation` into a `deleteTableRows` whose range is that row across the Table's columns at its live bounds, and the adapter sends it as a `deleteRange` shifting rows up (sheets-framework#52). Table writes are gathered before row writes, so a Table-end column insert queued in the same flush is already counted in the band: a band one column short would cover part of the Table, which Google refuses. A side-by-side Table and loose cells beside the Table stay where they are; a Table below in the same columns moves up with the shift.

## Column inserts land at the Table end, plain

`SheetMetaRaw.insertColumnAtEnd` is the one way to insert a column. It picks the index, the Table end past the inserts already queued, writes the new column's column ID, header and optional group heading, and returns the index; several on one sheet land side by side in queue order. The operation is `insertTableEndColumn`, and the adapter sends it as an `insertDimension` with `inheritFromBefore: true`, the only way a Table-end insert grows the live Table, then a `repeatCell` over the whole new column clearing its value, format and validation, because the insert copies those from its left neighbour ([what an insert copies](../testing.md)). The Table column type isn't copied, so the column starts Automatic. The flush grows the in-memory Table's end column for each insert, matching the live Table. An insert moves no Table column, so no write method checks a column index; cells right of the Table do shift. There is no mid-Table insert: one would come back as its own operation with its own measured `inheritFromBefore`.

## Growth is one `appendTableRows` per Table

`RowRaw.append` flags the row in its Table's write queue, so appends are grouped by `tableId` before any operation is built, and two Tables on one sheet grow apart. At gathering, `TableRaw.gatherAppendTableRowsOperation` expands a Table's appends into one `appendTableRows` (sheets-framework#59, #61):

1. `appendDimension`: one per sheet, sent first, sized `max(0, needed bottom − rowCount)` summed over every growth on the sheet. The sum is held on the sheet's write queue, and the local `rowCount` rises with it, so two growths never both count the same rows. An insert can't reach past the grid's last row, which is why this goes first.
2. Per Table, bottom Table first within a sheet: an `insertRange` (`ROWS`) over the Table's columns, below the last body row; an `updateTable` with `fields: "range"` to widen it, since an insert below a Table leaves its range alone; a `copyPaste` `PASTE_FORMAT` from the model row onto the new rows, which carries number formats and colours and extends a conditional-format rule ending at the last row; and a `copyPaste` `PASTE_DATA_VALIDATION` over each run of untyped columns only, since Google refuses cell validation in a typed column.
3. Then the value fills (`updateCells` / `repeatCell`) and formula fills (`pasteData`) already queued on the new rows.

The model row is the body row just above the first queued append. It is taken from the queued rows, not from the Table's end, because a same-run re-fetch resets the end while keeping the queued appends. The column types are the fetched ones, with any queued in the same flush laid over them, since `setTableColumnProperties` is sent first; a Table column with no fetched type refuses the growth and asks for a refetch. A row appended and deleted in the same flush still grows the Table and then goes out with the row deletes, so the appended rows after it keep their indexes. Growth is gathered before the Table-end column inserts are counted, because it is sent before them. `rowCount` and the column types ride the standing fetch masks, so growth adds no round trip.

**Growing a Table whose only body row is blank writes that row in place and inserts the rest.** Growth by n then sends the first row's fills into the blank row and an `appendTableRows` for the other n − 1, modelled on the blank row; growth by one sends only the fills. The reuse is decided at append time, not at gathering: `TableIdentified.appendRowDefault` hands out the blank row instead of calling `RowRaw.append`, so Raw only ever sees the n − 1 real appends, and their model row (the one above the first of them) is the blank row. Raw can't decide it, because the blank test skips formula and feedback columns, which only Identified resolves. When reuse applies and when it is refused: [blank row](./blank-row.md#the-append-path-reuses-the-blank-row).

Growth touches only the Table's own columns: a side-by-side neighbour and the cells between get no blank rows. Loose cells below the Table in its columns move down with the new rows, while cells beside them stay, so a loose block sticking out past the Table's columns is split.

## Stacked Tables grow in one batch

**The flusher gathers every Table's growth before any other write, then shifts the Tables below it, so the rest of the batch converts against the layout growth leaves.** Each `appendTableRows` records its Table and the rows it inserts, in the layout before growth. A Table whose header sits at or below those rows and whose columns overlap them is pushed down by their count, summed over every growth on the sheet (`TableCommonRaw.rowShiftFrom`); every shift is measured against the layout before growth and only then applied to the stored bounds (`SpreadsheetFlusherRaw._shiftTablesBelowGrowth`). Growth itself keeps the layout before growth, which is right because it goes out bottom Table first. The Table writes, row writes and deletes are gathered after the shift, so a fill or delete on a pushed-down Table lands on its rows after growth. A write that builds its operation when queued, such as a checkbox, a conditional-format rule or a protection, carries its rows from that moment, and the shift doesn't reach it. A lower Table wider than the grown one makes Google refuse the insert, since it would cover part of a Table.

## `updateColumnType` has three limits

**`updateColumnType` has three limits.** One update per fetch: the flush clears the Table's fetched column list, so another update before a refetch throws. It refuses, before anything is sent, when the same flush inserts a column on that sheet, and on a Table with a validated column, because a restore resets its dropdown style and colours.

## Per-cell writes merge value, formula and colour

Most writes queue per cell and flush as one `updateCells` request each; a cell's queued entry holds an optional value, an optional formula, and an optional background colour (`RgbColor` in the Source tier, mapped to Google `Color` only inside `GoogleSheetsAPI`), merged across writes, so a value and a colour on one cell still cost one request and neither can cancel the other. A value and a formula are mutually exclusive on that same entry: writing one drops the other. Each request's field mask is built from what that entry actually holds, so a colour-only write can't blank the cell's value and a value-only write can't blank its colour — which is how a per-cell message queued after a column-wide fill keeps the fill's colour unless it names its own.

## Column fills

A column write instead queues one sheet-level _fill_ per contiguous run of rows: `updateAllCells` fills every table data row of a column in one `repeatCell`, and `updateActiveCells` fills only the column's active rows, so stamping a selection costs no more requests than the selection is wide.

## Formula writes

`updateAllFormulas` / `updateActiveFormulas` are the formula-column siblings of those fills, and `updateFormula` is the per-cell sibling of `updateValue`. Both are exposed from `ColumnRaw`/`CellRaw` up through Identified and Named under the same names. Named type-restricts the three formula methods to formula columns; Identified runtime-refuses a formula write on a non-formula column; `GoogleSheetsAPI` serializes a string that already starts with `=` as `pasteData` with `PASTE_FORMULA` (RFC4180-quoted fields, tab delimiter, identical text on every row of a fill) and does not consult `isFormula`. **`pasteData` is required, not a style choice: a formula sent as `updateCells` `formulaValue` is stored verbatim, but a Table reference in it (`SUM(T[Col])`, `SINGLE(T[Col])`) evaluates to a parse error. The same text pasted, or sent through the values API as `USER_ENTERED`, parses (measured live, and again in sheets-framework#53, 2026-10-01).** So re-writing a formula read back from `userEnteredValue` must also go through `pasteData`. Colour on the same change still serializes as today's `repeatCell` / `updateCells` colour path, so a formula-plus-colour flush is two requests in one `batchUpdate`. A formula string that does not start with `=` throws before anything is queued — the `=` is not prepended. A formula write does not mirror into local cell state, so a later read in the same run still sees the old effective value (colour-only writes are the precedent).

## The last queued write wins between fills and cell writes

**The write queued last wins, whether it is a fill or a cell write, field by field.** Column fills still go out before cell writes, so a cell write queued after a fill sits on top of it; a fill queued after a cell write wins because queuing it erases the fields it sets from every cell entry already queued in its row range on that column. A value or formula clears the entry's value and formula, one slot; a colour clears its colour; an entry left with no fields is dropped. The order costs no extra request. A fill's last row is snapshotted when queued, so it never reaches a row appended after it. State is still mirrored row by row for _value_ fills — only the request collapses. `updateAllCells` and `updateAllFormulas` throw on a sheet that `TableRaw.removeRowsExcept` has pruned to a selection, since a whole-column fill ignores active rows and would reach exactly the rows the prune excluded.

## `findReplace` invalidates every read

**`findReplace` is the one write that names no coordinates, and it pays for that by invalidating every read.** It carries Google's own fields — `find`, `replacement`, `matchCase`, `matchEntireCell`, `searchByRegex`, `includeFormulas` — and a scope of a range, a sheet, or the whole spreadsheet, so `ColumnNamed`/`SheetNamed` build the scope while both strings stay plain: the value config governs neither, because Google matches the cell's text. It rides the same queue and the same dry run, and sits **after** cell writes because it reads the text as it stands mid-batch, so text queued beside it must land first. Two consequences follow from matching by content. Nothing can be mirrored into local state, since what matched is unknowable locally, so the flush marks **every** sheet's fetched cells stale — one rule rather than a scope-dependent one — and a read afterwards throws naming the findReplace until the next fetch clears it. A coordinate formula write (`updateFormula` / `updateAllFormulas` / `updateActiveFormulas`) is the other formula touch: it stamps a new formula onto a formula column by cell or fill as `pasteData` / `PASTE_FORMULA`, so Sheets runs the UI parser (table references included) rather than storing an unparsed `formulaValue`, and it does not invalidate reads. Colour may ride beside that paste in the same `batchUpdate`. `includeFormulas` remains the text-level rewrite of a formula already in place. `validateDataNotFormula` still refuses to _write a value_ onto a formula column, because a formula written as a value misbehaves in Apps Script.

## One queue shared by reference, and discarding it

That `spreadsheetStateRaw` is threaded **by reference** through `spreadsheetNamedProps` into every collaborator getter, so an endpoint, its `ConfigCoordinator`, and every operator beneath it all share one queue. A flush therefore commits everything queued anywhere in the run, not just what the calling object queued — which is why a failure path must `discardQueuedChanges()` before writing status, or the `finally` flush ships a half-finished sync. Discarding resets both write queues as groups (the spreadsheet's `writeQueue.operations` and every sheet's `writeQueue`) rather than re-initializing individual fields. It leaves the working view reflecting writes that never happened, so it's a terminal step only.
