# Stacked Tables shift within one batch

Map fragment. Sibling headings live in this folder.

Growth, a column insert and a row delete each move the other Tables on their sheet. How the rest of the batch converts against the moved layout, and the refusals that keep a neighbour whole.

## Every coordinate converts against the layout before it

**Every sheet coordinate is converted at gathering against the layout the earlier operations in the same batch leave.** Three operations move other Tables: growth pushes the Tables below whose columns overlap down, a column insert pushes the Tables to the right whose rows overlap right, and a row delete pulls the Tables below whose columns overlap up. Each shift is measured against the layout before its operation and only then applied to the stored bounds (`SpreadsheetFlusherRaw._measuredShifts`), so no shift sees another.

## Growth pushes the Tables below down

**The flusher gathers every Table's growth before any other write, then shifts the Tables below it, so the rest of the batch converts against the layout growth leaves.** Each `appendTableRows` records its Table and the rows it inserts, in the layout before growth. A Table whose header sits at or below those rows and whose columns overlap them is pushed down by their count, summed over every growth on the sheet (`TableCommonRaw.rowShiftFrom`, `SpreadsheetFlusherRaw._shiftTablesBelowGrowth`). Growth itself keeps the layout before growth, which is right because it goes out bottom Table first. The Table writes, row writes and deletes are gathered after the shift, so a fill or delete on a pushed-down Table lands on its rows after growth. A checkbox, a conditional-format add and a column, row or cell protection are Table writes too: each is queued on its Table with a Table-relative range (`TableGridRange`) and converts at gathering, so it lands on a pushed-down or pushed-right Table's rows and columns after the shifts (sheets-framework#121). Only a whole-sheet protection, which has no Table rows, is built when queued. A protection on a Table whose properties haven't arrived is refused when queued, as every other Table write is, since no shift would carry it. A rule or protection removal stays sheet-addressed, since it matches the fetched layout before this batch. A lower Table wider than the grown one makes Google refuse the insert, since it would cover part of a Table; the refusal is reworded, as below.

## A row delete pulls the Tables below up

**A row delete pulls the Tables below up once every write sent before it is gathered (sheets-framework#122).** Fills, checkboxes, find-and-replaces, conditional-format adds and protections go out before the deletes, so they are gathered against the layout before them; Google carries a rule's or protection's range up with the rows, and shrinks a range over a deleted row, as it does for any rule or protection already on the sheet. Then the flusher shifts up each Table whose header sits at or below a delete and whose columns overlap it, by the rows deleted above it (`TableCommonRaw.rowPullFrom`, `SpreadsheetFlusherRaw._shiftTablesBelowRowDeletes`). A Table's own deletes sit below its header, so they never move it. Sorts, the one sheet-coordinate write sent after the deletes, are gathered after that shift, so a lower Table's sort spans its rows after them. Deletes go out highest row first, so a lower Table's are sent before the upper Table's pull it up. A `raw` operation, sent last, is built by its caller, so no shift reaches it.

## A column insert pushes the Tables to its right

**A column insert pushes the Tables to its right the same way, after growth's shift.** The flusher gathers every Table's column inserts against the layout growth leaves, then shifts right, by the inserted count, each Table whose first column sits at or past an insert's first column and whose head rows plus Table range overlap its band (`TableCommonRaw.columnShiftFrom`, `SpreadsheetFlusherRaw._shiftTablesRightOfColumnInserts`). Inserts go out rightmost Table first within a sheet, so none moves a Table whose insert is still to come. The rest of the batch is gathered after both shifts, so a write to a pushed-right Table lands at its new columns.

## A column insert refuses to split a neighbour from its head rows

**A column insert refuses to split a neighbour from its head rows (sheets-framework#123).** Google refuses an insert only when its band covers part of another Table's range, and it can't see head rows. So it lets through a band that reaches a neighbour's head rows but not its Table, at the band's bottom edge, or the neighbour's Table but not all its head rows, at the top edge. At gathering, before anything is sent, `TableRaw.gatherInsertTableEndColumnsOperation` refuses if any known Table on the sheet that starts at or past the insert's first column has head rows plus Table range straddling either edge of the band (`TableCommonRaw.isSplitBy`). The refusal names both Tables and the band's 1-based rows. That covers a taller neighbour too, so past the check a neighbour the band reaches sits wholly inside it, and the shift moves it whole. A Table the app doesn't know about has no head rows, so Google's own refusal covers it, reworded as below. A recorded Table the zone missed, whose head rows it can't see either, stops the insert first ([table placement](./table-placement.md#a-column-insert-uses-every-table-on-its-sheet)). Growth and row deletes need no such check: they shift cells within a Table's columns, which its head rows span too, so a band reaching a neighbour's head rows also reaches its Table, which Google refuses.

## Google's partial-Table refusal is reworded

**Google's partial-Table refusal is reworded (sheets-framework#94).** Google refuses an insert over part of a Table with `You cannot insert or delete cells over part of a table.`, naming only the request. `GoogleSheetsAPI.flush` traces that request back to its operation and throws a `PartialTableRefusal` carrying it. `SpreadsheetFlusherRaw` finds the growth or column insert that gathered the operation, then fetches the sheet's Tables, one read on the failure path only, to find the one the insert would split. The fetch also sees Tables the app doesn't know. The batch was refused whole, so the fetched layout is from before this batch's growth; each fetched Table is pushed down by that growth first, as `TableCommonRaw.rowShiftFrom` pushes a known one, since a column insert is measured after it. A growth's refusal names both Tables and the sheet, and says to make the lower Table no wider than the grown one, or move it. A column insert's names both Tables and the sheet, and says to move the split Table wholly inside or outside the band's rows. Any other refusal, such as a row delete's, goes up as Google sent it. There's no up-front check of the layout.
