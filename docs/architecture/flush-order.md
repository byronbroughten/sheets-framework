# Flush order

Map fragment. Sibling headings live in this folder. How a write reaches the queue: [queued writes](./queued-writes.md).

One `batchUpdate` per flush sends the queued operations in a fixed order by kind. Why each kind sits where it does, and how add-sheet and add-Table lead the batch.

## Flush order

Within a flush the requests go out in a fixed order: add-sheet, then add-Table, then sheet renames, Table renames, Table column-property sets, Table growth, column inserts, column fills, cell writes, checkbox validations, find-and-replaces, conditional-format deletes highest-index-first, conditional-format adds, edit-protection deletes, edit-protection adds, then row deletes highest-index-first, then sorts, then raw. A column-property set is one `updateTable` per Table, sending every fetched column's `columnName` and type, because a partial `columnProperties` list replaces the rest. It goes first so a header write in the same flush renames the column rather than being reverted by the stale name. Growth therefore lands **before** the deletes queued beside it, and same-sheet deletes go descending because each one shifts the rows beneath it. Conditional-format deletes use the same descending-index reason as row deletes: each removal renumbers the rules beneath it. Adds follow those deletes so a remove-then-re-add in one flush lands in the order it was queued. Edit-protection deletes are by id, so they do not need descending order.

## Add-sheet and add-Table lead the batch

Add-sheet and add-Table lead the batch because a Table can only be added to a tab the same batch has created, and both are queued on the spreadsheet (`SpreadsheetRaw.gatherAddSheetOperation` / `gatherAddTableOperation`) rather than on a sheet, since a tab that does not exist yet has no sheet state to hold them and nothing is gathered per sheet. Google refuses an add-sheet at a GID another tab already holds, so the request always carries `sheetId` and the refusal comes back from the API. An add-Table operation goes out as two requests: an `addTable` under a random `tableId` the framework mints when queued (`tbl-` and ten hex digits, unless the caller supplies one), then an `updateTable` carrying its column names and types, because Google writes `addTable`'s own column names three columns right of the Table, and fails with a 500 when those columns don't exist (measured on the dev spreadsheet, 23 September 2026). Google would mint an ID itself, but only in the reply, too late for that `updateTable` (sheets-framework#59).

A cell value on an added tab is queued on the spreadsheet too, by `SpreadsheetRaw.gatherAddedSheetFillCellOperation`: it is built when queued and sent in the cell writes slot, so it lands on the tab the same batch created. It is refused unless that GID's add-sheet is queued in the same flush, which keeps a write to an existing tab going through `CellRaw`. A checkbox (a `BOOLEAN` data-validation rule) is queued on its Table by `CellRaw.addCheckboxValidation` and gathered at flush time, or on an added tab built when queued by `SpreadsheetRaw.gatherAddedSheetCheckboxValidationOperation` under the same add-sheet guard, and sent right after the cell writes, so a seeded unticked `false` is written before its rule.
