# Edit protections (edit warnings and edit locks)

Map fragment. Sibling headings live in this folder.

What an edit warning and an edit lock are, how the framework reads, matches and writes them, the ranges it names, and the live probes behind those choices.

## Warnings, locks and unmodelable protections

An **edit protection** (`EditProtection`) is an **edit warning**, an **edit lock**, or an unmodelable protection the framework leaves alone. The Google API type stays `ProtectedRange` at the adapter boundary, the way `ConditionalFormat` does. A warning prompts anyone, the owner included, and still lets the edit through. A lock takes optional `users` and `groups`. Unprotected ranges are representable only on a whole-sheet declaration.

## Lock editors and the owner lockout

A lock that names no editors inherits the spreadsheet's editors (live 2026-09-17: two gmail users and a service account) and does not stop them, so it is not a fence. A lock that names users reads back with exactly those users — Google does not add the inherited set. One such lock left the spreadsheet owner unable to edit Column currency data cells on `test`, except the last row, which sat outside the bounded range. **Why is unresolved.** The likely cause is address form rather than a broken guarantee: Gmail treats dotted and undotted addresses as one mailbox for delivery, but Google account identity uses the address as registered, so a lock naming `byron.broughten@gmail.com` on a file whose editor is `byronbroughten@gmail.com` may name a stranger — in which case blocking the owner is correct. The probe chores were never committed, so neither the string sent nor the string read back is recoverable; settle this before building anything on a list of editor addresses. The stronger claim once recorded here — that Apps Script's "the owner can never be removed" fails for a REST write — is withdrawn as unsupported. Separately, the GUI refuses to create a lock that would lock the acting user out and the API does not, so a developer can fence themselves out through this framework in a way the GUI would have prevented; there is no guard, because the framework does not know which account it is acting as.

## Reading protections

Reads use a plain spreadsheet get with a `protectedRanges` fields mask. `getByDataFilter` also returns them (live 2026-09-17, same payload as the plain get on `test`), unlike conditional formats; the adapter still uses the plain get so one request covers every sheet. Google omits an empty list, so a sheet missing from that read's protections has none, not "unfetched"; it omits zero-valued range fields the same way, which read back as 0. A range with no row or column bounds at all is a whole sheet. An open-ended column protection (start row and column bounds, no `endRowIndex`) reads back open-ended. Google lists `editors` on a warning too; a warning reads back with no users or groups, since it never uses them.

Every protection the payload holds is mapped, one for one, in order. A protection backed by a named range or a Table, or that sets `domainUsersCanEdit`, becomes an explicit unmodelable value that still carries its id and can still be removed by id. Google's `ProtectedRange` has no Table id; a Table-backed protection is unmodelable when it carries `namedRangeId`, which is the only Table signal on that resource.

## Matching: identity is content

Identity is content: range, kind, editors, unprotected ranges and description. An add queues nothing when a fetched or already-queued protection matches it on everything but editors and holds every editor it declares; a lock that names none comes back with extra inherited editors, so an exact editor match would re-add it every run. Removal is by exact range, exact content, description or id — never by overlap — so a hand-set protection is left alone until it is named.

## Queueing writes and stale indexes

The update queue emits delete-protection then add-protection after the conditional-format adds and before raw requests. Deletes are by id. A write whose range or unprotected ranges carry row coordinates read off the sheet refuses to queue while that sheet's row indexes are stale. A whole-column range (start row 0, column bounds, no end row) is not that shape: its start row is a constant, so it refuses while the sheet's **column** indexes are stale instead, using the same watermark cell and column writes already consult. A whole-sheet protection with no unprotected ranges demands neither. A flush that added or deleted a protection marks that sheet's protection list stale; reading or mutating it again requires a refetch. The add reply carries the new id; the framework does not integrate it, because the refetch is required.

## Named ranges a protection can cover

Named structures: the sheet data range (`addEditWarning` / `addEditLock`), the whole sheet (`…WholeSheet`), a bookkeeping row or the Table header row, a column's data range, an open-ended column range from a start row (`gridRangeFromRow` / `addEditWarningFromRow`), a whole column (`…WholeColumn`: the same getter at row 0), a column's header / column-ID / column-group heading cell, and a single cell. Raw has a whole-row range helper. A whole-column range is a grid range, so it can never equal a whole-sheet range. An open-ended data range starts at the first data row; a whole-column range starts at the top of the sheet and therefore covers the bookkeeping rows as well as rows added later. Whether a range with no end row follows the grid when the sheet grows past its current row count is open, and not worth probing until something depends on it.

## Probe 2026-09-17: data-column ranges and appended rows

**Probe (2026-09-17), `test`, with follow-up checks the same day.** The Table already had many data rows (last index 15, end 16), so the API append landed at the bottom (row 17), not in the blank at row 7. Bounded data-column protections (`B5:B16`, `E5:E16`, `I5:I16`) did not grow on that append or on typing below the Table, and the appended row was unprotected. An open-ended protection *does* cover rows added later: a warning reaching below the data fired on a cell under the Table, and still fired on a cell in a Table row added afterwards. A range with a **concrete** last row does not follow grid growth — one stayed at its end row when 1000 rows were added to the sheet. Whether a range with no end row follows grid growth past the sheet's row count at creation is open, and not worth probing until something depends on it. The GUI translates a `$E5:E` typed into it to a concrete end at the sheet's current last row, so the GUI's open-ended spelling and the API's are not the same thing. The owner got the warning prompt on ID and was neither blocked nor prompted on Num (lock naming no editors); a cell carrying both a lock and a warning still prompts, as long as the lock permits the person editing. A warning carries no custom message — the description reaches the Protected sheets and ranges sidebar and this framework's matching, never the prompt. Column drag was refused for every column while those protections were present; warning-only vs lock was not isolated. Cleanup deleted row 17 and the four probe protections; a later get omits `protectedRanges` on `test`. **Floor data-column range: open-ended**, because a bounded range does not cover rows added later and an open-ended one does. An earlier write-up of this probe recorded the opposite — that the open-ended warning did not cover the new Table row — and justified the same decision by the range merely *reading back* open-ended, which is a proxy for coverage rather than coverage itself.

## Probe 2026-09-18: whole-sheet warning with unprotected ranges

**Probe (2026-09-18), whole-sheet warning with unprotected ranges.** A warning-only whole-sheet protection prompts on tab rename, tab delete, and column insert. An edit inside an unprotected range does not prompt. An inserted column inherits the unprotected range only when inserted strictly inside it; at either edge it sits outside until the next floor sync adds it — a gap the floor accepts. A whole-grid unprotected range still prompts on column insert; a whole-column unprotected range does not prompt when inserting strictly inside it. Why those two shapes disagree is open.

## Check 2026-09-19: editable ranges shift with a deleted row

**Check (2026-09-19), a protection's editable range shifts with a row deleted above it.** On the live spreadsheet, an editable range of `B6:D9` read back as `B5:D8` after a row above it was deleted. The config-sheet floor's carve-outs rely on it: it computes the self-describing rows' indexes from the rows as fetched, before the sync moves any, and the ranges follow the rows the sync deletes. Rows the sync appends land below the carve-outs, inside the open-ended tail. A self-describing row that does not exist yet (a fresh Sheet Config, before the sync appends its rows) is not carved on that run; the next sync carves it. There is no second pass.
