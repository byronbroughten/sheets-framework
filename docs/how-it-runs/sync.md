# sync and configs-diff

**`sync` plans `alterations.ts` against the live sheet and the previous configs, refreshes the config files, and sends the plan only with `--send`; its exit code says whether the run did what it set out to ([exit codes](#syncs-exit-codes)). `configs-diff` compares those files with `HEAD`, with no credential and no Sheets call.**

## What a sync run does

`sheets-framework sync` (`npm run sync` in a package) runs `SyncCoordinator.run` with the pending alterations in `alterations.ts` as intended state and the previous `idNameMap.ts` as the map its entries are checked against; a missing `alterations.ts` is an empty one and a missing map an empty map. A bare run reads the live sheet, plans, and refreshes the configs from what it read, but sends nothing. `--send` sends the plan as well, any missing column IDs to business sheets' header rows, and a Fill Row IDs checkbox into each empty action-row cell above an ID column, in one flush; a non-empty cell there is left alone. After the regen it fills every blank ID cell, planned from the fresh configs, as its own send; that is the only row data `sync` writes. A fill send that throws still leaves the configs written, and the run reports `STOPPED PARTWAY` with the error's message. A Table whose ID is its first column gets the `idFirst` notice, since the Table name chip hides its checkbox. Either way, it prints the run's result through `SyncRunReport`.

## Adding columns with newColumns

**`newColumns` is sendable, and `sync` mints each new column's ID.** Each entry is a group, `{ columns, before? }`, whose columns are inserted together, in order, before its `before`, or appended in order when it has none; a lone new column is a group of one. A column takes only `header` and `emptyValueAllowed`; `formula` and `columnType` are refused as not sendable yet, since they need a write after the insert (`sendableTraits.newColumn`). Two entries with the same `before`, or a `before` that a `moves` group on the same Table also names, are refused before the read; a refusal or stop on a group's column names it by `newColumns[i].columns[j]`, and on its `before` by `newColumns[i].before`.

## Creating Tables with newTabs and newTables

**`newTabs` and a tab's `newTables` are sendable, several new Tables on one tab in one run, and `sync` mints each new Table's ID, ID prefix and column IDs.** The working view lists each Table the creation flush adds, and each tab its `addSheet` adds, so a later new Table on the tab is placed right of it; a new tab's first Table sizes the `addSheet` and each later one grows it (`SpreadsheetTableCreatorRaw`). A new tab's `addSheet` carries its title, and its other traits arrive in the same run: once every Table is created, in its own flush, the run refetches the sheet properties and sends them as an existing tab's traits are sent, in one more flush ([flush order](../generated-data/config-sync.md#which-flush-sends-what)). So a new tab's `before` may name an existing tab or another `newTabs` entry by its `title`. One naming neither, or a tab the same run deletes, is refused before the read; one naming a tab the same run retitles reaches it by its GID in the previous ID-name map. A dry run plans the traits but, with no tab to reach, never queues them. A new Table's `conditionalFormats.remove` and `replace` are refused as not sendable yet. A new Table's `conditionalFormats.add` rules name its columns by the `columnName` each header gives, and are refused before the read as `newColumns` rules are. They are compiled against the range the creation gives the Table, which follows the run's earlier column sends, and are sent in the creation's flush after its `addTable`. A new Table whose name a live Table has, or a new tab whose title is taken, stops the run before any send (`TableConfigsOperator.newTableStops`).

**A new Table's column `formula` and `columnType` go in the flush that creates it**: the type and rule in the creation's column properties, so `dropdownStyleReset` doesn't apply, and the formula filled into every body row (`SpreadsheetTableCreatorRaw.createTable`). Both compile when the Table's IDs are minted, before any send, and a brace naming the new Table resolves against its planned columns by the `columnName` each header gives (`columnNameOfHeader`). A seed value in a formula column is refused.

## Moving columns with moves

**A Table entry's `moves` list alone places existing columns: each `{ columns, before }` group goes, in list order, to sit together in its order immediately before its target, unless live already has that order**, through `TableRaw.moveColumns` after the run's column deletions and inserts have flushed (`ColumnConfigsOperator.planColumnMoves`); a column entry has no `before`. Live's reading of a column's place is the next column on the sheet, and the configs never record it. A group already in place is met, not moved, and a group lands when the refetch shows it in place. A move to the first position goes as the columns before it moving right, since an insert at a Table's first column lands outside it ([observed](../sheets-behaviour.md#moving-columns-within-a-table)); moving the last column to the front is unmeasured, so it is refused before anything is sent. The entry refuser refuses two groups with one `before`, a column in two groups and a `before` some group moves, so every group can hold at once.

## sync's entered-data gate and --confirm

**A formula alteration is sent by `--send`**: its brace text ([forms](../architecture/cell-writes.md)) is compiled to live Table references and filled into every body row through `pasteData`, by `ColumnConfigsOperator.updateFormulas`. `SyncEntryRefuser` refuses a malformed brace before any send.

**A column entry's `columnType` is sent by `--send`**: its type and rule, the rule's `=`-values compiled from brace form, go through `TableRaw`'s column-type write (`ColumnConfigsOperator.updateColumnTypes`). That write resets the style of every dropdown on the Table ([observed](../sheets-behaviour.md#creating-and-updating-tables)), so the plan item's `dropdownReset` effect lists them under the app's `dropdownStyleReset`, and `"ask"` holds the send. A dropdown the send itself removes, its intended rule `null`, has no style to keep, so it isn't listed and doesn't hold the send.

**A `sync` command can lose entered data only while holding `--confirm`** ([ADR 0034](../adr/0034-hold-entered-data-loss-at-the-node-hosts-adapter-until-a-hash-bound-confirm.md)); a chore's gate: [chore dry run](./chore-dry-run.md). An unstopped dry run flushes its plan after its files are built, for the Node host's gate to judge and withhold; `SyncRunProps.isHostWithholding` turns that flush on, and only the Node host's `sync` sets it. Just before that flush, or a send's, the run reads the cells the gate judges: every column a deletion or a sent formula touches, and each deleted Table or tab still on the sheet (`enteredDataReads`). When the gate holds anything, the dry run writes every held item and its value to the package's `.probe/sync-held.json`, prints that path, the held list (each column past 20 lines as counts, with their sum) and the token, then "Rerun with `--send --confirm <token>` to send these". `--send --confirm <token>` reads that file, a missing or unreadable one counting as mismatched, and sends only when the token and the list still match. A refused send writes no file and says only "rerun the dry run": `STOPPED` before any flush landed, `STOPPED PARTWAY` after, with the landed flushes reported. A batch Google refuses, such as a column move beside a taller Table, stops the send the same way, its line carrying Google's refusal reworded to name both Tables ([stacked tables](../architecture/stacked-tables.md#googles-partial-table-refusal-is-reworded)).

## Forcing one trait with --force

**`--force <table>/<column>/<trait>` sends one column trait's value from `alterations.ts` over the sheet's, for that run only** ([#274](https://github.com/byronbroughten/sheets-framework/issues/274)). Without it, a trait both `alterations.ts` and the sheet changed since the configs is a conflict that stops the run. The report's conflict block offers its ways out: adopt, ask and, for a column's trait, force, which says it needs the developer's yes for that trait and prints the flag to pass (`Flag: --force <table>/<column>/<trait>`). A Table's or tab's own trait, or a deleted column's, has no force to offer. The flag is read from the command line and nothing carries it to the next run (`parseForcedTraits` in `scripts/sync.ts`), so the same conflict stops the next run without it. The entered-data gate holds each forced trait, listed as "sent over the live value by --force", so it is sent only under `--send --confirm <token>`; it lands as `set to X, over the sheet's Y`. In byro-repo, the tier gate asks before a `sync` holding `--force` ([byro-repo#564](https://github.com/byronbroughten/byro-repo/issues/564)).

## What sync writes

A refused run writes no file. Every other run writes every generated file ([the list](../generated-data.md#the-generated-half-and-the-hand-written-half)), and rewrites `alterations.ts` only when the run returns it, with the landed alterations removed and every name the regen renamed rewritten. An alteration the configs and the live sheet already both hold, or an order the live sheet already holds, since the configs hold no order, is never planned; an unstopped send counts it as landed and removes it, and the report lists it under its own "Already met" heading.

**A pending entry still names what it meant after a rename**: when the regen gives a Table, column or tab ID a new name, every run that writes files, a bare or stopped one included, rewrites the entry keys, `before:` names and `moves` groups' column names that used the old one (`SyncNameRewriter`, [ADR 0035](../adr/0035-key-alterations-by-codebase-name-and-have-sync-rewrite-pending-names-on-a-rename.md)). It rewrites the braces and `Table[Header]` references in pending formula text and rule condition values, a new Table's included but outside string literals, and a rule's `columns` and its `remove` or `replace` handles. Endpoint and chore code are never rewritten. The report lists each rewrite and each Table, tab or column name that now points at another ID under Configs, and shows a rewritten entry's subject as `table › newName (you wrote oldName; columnId)`. What an agent does after a run that lists a moved name: [`src/01_SpreadsheetSchema/AGENTS.md`](../../src/01_SpreadsheetSchema/AGENTS.md).

When the `generatedDir`'s parent holds no `alterations.ts`, it creates one in the format sync emits, holding an empty `makePendingAlterations({})`. It prints the configs diff before the report, then runs the package's `npm run tsc`, and fails if that fails.

## sync's exit codes

The run exits 1 when it stopped, was refused, held a flush that stopped a send (before any flush landed or partway), or sent with an item that didn't land (a sent header or Table name Sheets kept another value for); and when the package's `npm run tsc` fails afterward. It exits 0 otherwise: a ready dry run, held items included, or a send where everything landed. `syncExitCode` in `scripts/sync.ts` decides it.

## What configs-diff prints

`sheets-framework configs-diff` prints what changed in those config files since `HEAD`: Tables, tabs, columns and values added, removed or renamed (matched by `tableId`, `sheetGid` and `columnId`), prefixes added to or dropped from the retired list, conditional format rules added or removed under their Table or tab (matched by rule handle), and each changed field's old and new values, or "No config changes." It is read-only, with no credential and no Sheets call, and `sync` prints the same summary when it finishes, so the summary is how to review a regen without reading the large `columnConfigs.ts`.
