# The config sheets and the regen

Part of [generated data](../generated-data.md). The regen reads the live sheet and the previous configs; it neither reads nor writes the Table Config and Column Config tabs.

## Which config-sheet columns get a cell

**A live config-sheet column exists so the host can identify the row (Table ID on Table Config; Table ID and Column ID on Column Config) or so a human can use it on that sheet** (readable identity such as Table name, sheet title and header; declarations such as Empty value allowed and Let api access; helper formulas). Sampled generated traits — `isFormula`, `valueName`, `hasIdColumn`, `idPrefix` — do not earn a cell. Emit writes those traits into the generated files from the described live columns; leftover Is formula / Value title / Has ID column / ID prefix cells, while those columns still exist, are ignored (#33, #87). A Column Config row is identified by its Table ID and Column ID together, never by Column ID alone, because a duplicated tab repeats the original's column IDs (#101).

## The regen leaves the config tabs alone

`SyncCoordinator.run()` takes API access from a Table's presence in the previous configs, changed by a `letApiAccess` alteration, and `emptyValueAllowed`, a column's `header`, `formula` and `deleted` and a Table's `name` and `deleted` from the three-way plan over pending alterations, the previous configs and the live sheet. Only an unstopped send writes: the planned sends and the missing column IDs on business sheets' header rows, in one flush, then any column deletions in a flush of their own ([why](../architecture/table-columns.md)). A column deletion is planned as `delete the column` and sent through `TableRaw.deleteColumn`, rightmost first on each Table. A Table deletion is planned as `delete the Table` whenever the live Table exists, and sent in the first flush through `TableRaw.queueDelete`, which leaves its tab. Its plan item names, by rule handle, the conditional-format rules wholly over the Table, each range bounded and inside the header row through the last row over its columns, which go with it; each other rule touching the Table is listed with its tab, ranges and formula as partly over it, and stays on the sheet with nothing sent. Under Check before sending, each deleted Table gets one outside-references check listing the formulas outside it that name it, each with its column's body-row range and its formula in brace form, and its plan item counts them; they will read blank cells, since Sheets rewrites a deleted Table's references to its old body rows ([observed](../sheets-behaviour.md#creating-and-updating-tables)). The formulas come from the run's live read of every API-access Table's formula columns, Tables deleted in the same run left out, so a formula a person edited since the last sync is checked as it now stands. A formula anywhere else, outside a Table or in a Table without API access, isn't checked and nothing is read for it; whenever a Table deletion is planned a notice says so. A Table's `conditionalFormats.remove` handle is matched against the rule handles the configs would record from the run's read, unmodelable rules included, planned as `remove the rule` and sent in the first flush as `deleteConditionalFormatRule` at the rule's fetched index, a sheet's deletes highest index first; a handle no rule has now stops the run as no such rule, listing the Table's handles, and a removal is reported under Didn't land when the refetch finds more copies of its rule than the send should leave; a handle listed twice is one removal. A `conditionalFormats.replace` handle is matched the same way and planned as `replace the rule`; its rule spans the body rows of its `columns` (`"all"` meaning every column), its formula compiled by `BraceFormula.compileForRule` against the planned layout, and is sent as `updateConditionalFormatRule` at the rule's index after the column deletions' flush ([why](../architecture/conditional-format-rules.md)). A replace handle no rule has stops the run as no such rule, and one naming an unmodelable rule stops it before any send, since that rule can only be removed; a replacement is reported under Didn't land when the refetch finds no rule with the compiled rule's handle. A rule's `bold`, `italic` or `strikethrough`, in `add` or `replace`, is refused before the read as not sendable yet. A Table a person deleted from the sheet is no conflict: an entry naming it plans nothing, the configs drop it, its prefix retires, and the report names it under Notices. A tab a person deleted is no conflict either: its Tables drop the same way, and the report names the tab under Notices before its Tables' lines. A Table or column deletion on a tab the run also deletes is refused before the read, since the tab's deletion already takes the Table. A dry run on a host that withholds flushes them too, for the entered-data gate ([sync's gate](../how-it-runs/sync.md#syncs-entered-data-gate-and---confirm)). A column `header` goes as an `updateCells` write of its header cell and a Table `name` as `updateTable` with `fields: name`, so both keep dropdown styles and rewrite `Table[Header]` references. When a header, a name, a formula, a Table or column deletion or a rule removal or replacement was sent, the run refetches after the flush and emits every file from that read, so the configs follow the new header, key the Table by its new name and drop a deleted Table or column, as does the ID-name map. A deletion the refetch still shows the Table or column for is reported under Didn't land, and its entry stays in `alterations.ts`. Each sent header or name that the refetch shows Sheets kept another value for is reported under Didn't land as `set to X; Sheets kept Y`: the configs take the value Sheets kept, and the entry stays in `alterations.ts`, left out of Landed. The summary counts both (`N alteration(s) landed; M didn't land`). A bare or stopped run mints no column ID and leaves a column without one out of its configs. Every run past the refusals returns every generated file, and `alterations.ts`'s source only when an alteration landed or a rename rewrote a pending entry's names ([the rewrite](../how-it-runs/sync.md)). There is no sync endpoint, no `syncConfigSheetRows` and no correction pass over the config tabs' rows. The [config-sheet floor](./config-sheet-floor.md) is the `ensureConfigSheetFloor` chore's alone; `npm run sync` does not run it.

A live ID prefix that differs from the configs stops the run before any write (`idPrefixGuard`, run over every Table, sharing the retired prefixes with the title-derived prefix).
