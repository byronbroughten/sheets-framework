# The config sheets and the regen

Part of [generated data](../generated-data.md). The regen reads the live sheet and the previous configs; it neither reads nor writes the Table Config and Column Config tabs.

## Which config-sheet columns get a cell

**A live config-sheet column exists so the host can identify the row (Table ID on Table Config; Table ID and Column ID on Column Config) or so a human can use it on that sheet** (readable identity such as Table name, sheet title and header; declarations such as Empty value allowed and Let api access; helper formulas). Sampled generated traits — `isFormula`, `valueName`, `hasIdColumn`, `idPrefix` — do not earn a cell. Emit writes those traits into the generated files from the described live columns; leftover Is formula / Value title / Has ID column / ID prefix cells, while those columns still exist, are ignored (#33, #87). A Column Config row is identified by its Table ID and Column ID together, never by Column ID alone, because a duplicated tab repeats the original's column IDs (#101).

## The regen leaves the config tabs alone

`SyncCoordinator.run()` takes API access from a Table's presence in the previous configs, changed by a `letApiAccess` alteration, and `emptyValueAllowed`, a column's `header` and a Table's `name` from the three-way plan over pending alterations, the previous configs and the live sheet. Only an unstopped send writes: the planned sends and the missing column IDs on business sheets' header rows, in one flush. An unstopped dry run flushes the same writes after its files are built only when `SyncRunProps.isHostWithholding` says the host withholds them, which only the Node host's `sync` sets, so the entered-data gate judges what a send would write ([sync](../how-it-runs/sync.md#what-a-sync-run-does)). A column `header` goes as an `updateCells` write of its header cell and a Table `name` as `updateTable` with `fields: name`, so both keep dropdown styles and rewrite `Table[Header]` references. When either was sent, the run refetches after the flush and emits every file from that read, so the configs follow the new header and key the Table by its new name. Each sent header or name that the refetch shows Sheets kept another value for is reported under Didn't land as `set to X; Sheets kept Y`: the configs take the value Sheets kept, and the entry stays in `alterations.ts`, left out of Landed. The summary counts both (`N alteration(s) landed; M didn't land`). A bare or stopped run mints no column ID and leaves a column without one out of its configs. Every run past the refusals returns every generated file, and `alterations.ts`'s source only when an alteration landed. There is no sync endpoint, no `syncConfigSheetRows` and no correction pass over the config tabs' rows. The [config-sheet floor](./config-sheet-floor.md) is the `ensureConfigSheetFloor` chore's alone; `npm run sync` does not run it.

A live ID prefix that differs from the configs stops the run before any write (`idPrefixGuard`, run over every Table, sharing the retired prefixes with the title-derived prefix).
