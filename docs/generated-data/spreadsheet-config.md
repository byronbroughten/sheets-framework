# `spreadsheetConfig`: the layout record

Part of [generated data](../generated-data.md). It holds the constraints every sheet must be written to satisfy, and a regen fails closed on a changed layout value.

## How `spreadsheetConfig` is generated

**`spreadsheetConfig`** (`generated/spreadsheetConfig.ts`) — the constraints every sheet in the spreadsheet must be written to satisfy: uniform-row indexes, the ID delimiter, and the ID and Name headers. The test for what belongs here is *scope, not kind* — a constant governing how any sheet must be authored belongs here even if only one tier reads it; a constant governing one tier's internal behavior does not. Config-sheet GIDs live on `sheetConfigs`, not here. Generated by `SpreadsheetConfigOperator` (`05_Operators`) from the live "Spreadsheet Config" sheet: one data row of base-1 indexes (labels say so) translated once into today's base-0 field names. The first data row is the Table header row plus one and is not stored on the layout record. The four uniform-row indexes must be integers ≥ 0, pairwise distinct, and none may equal the first data row; the generated constructor and live overlay share that check. Extra columns are ignored. Spreadsheet Config cells are never rewritten by the sync; the one exception is Table menu space's data cell, which the config-sheet floor writes as `Not used` (the floor seed's `dataValue`) and restores if it changes. The fetch reads the first data row through the Named tier at the compiled layout. A regen or checkbox sync fails closed unless that sheet has a Table with exactly one data row, every guaranteed cell non-blank, and every layout value but ID header and Name header equal to the compiled one; the refusal names each changed value with the one it expects, in base 1.
